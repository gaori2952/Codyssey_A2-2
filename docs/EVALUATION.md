# 프롬프트 설계 및 평가 문서

## 1. 프롬프트 설계 및 설계 이유

이 프로젝트는 뉴스 수집·정제·분석 파이프라인에서 AI 요약과 비교 분석을 수행합니다. 단순히 모델에 기사 내용을 던져주는 것만으로는 결과 품질이 불안정할 수 있으므로, 다음 목적에 맞게 프롬프트를 설계합니다.

- 기사에 없는 내용을 추론하지 않도록 제한
- 사실 중심의 요약과 분석 유지
- 소스별 차이 비교를 구조화해 정량적 비교 가능하게 만들기
- 동일 이슈 비교에서 강조점과 표현 차이를 일관되게 추출
- 출력 형식을 JSON으로 고정해 후속 파싱 오류를 줄이기

핵심 전략은 "모델에 해야 할 일, 금지할 일, 출력 구조를 명확히 제시하는 것"입니다.

### 기대 출력 형태

#### 요약 프롬프트

입력:
- 기사 제목
- 기사 본문

출력:
- 3문장 이내
- 한국어 사실 중심 서술
- 추정/추론 금지

예시:

```text
제목: OpenAI, 새 모델 공개
본문: ...
```

```text
OpenAI가 새 AI 모델을 공개하면서 업계 경쟁이 가속화되고 있다. 공개된 모델은 기존 제품 대비 추론 속도와 효율성을 개선했다. 다만 실제 서비스 적용 시 비용과 검증 절차에 대한 논의가 계속되고 있다.
```

#### 분석 프롬프트

입력:
- 여러 기사 요약 목록

출력:
- JSON 객체
- 키: trend, keywords, issues, implications

예시:

```json
{
  "trend": "AI 모델 경쟁이 고성능 추론과 비용 효율성으로 이동하고 있다.",
  "keywords": "추론 속도, 비용 최적화, 모델 공개, 기업 적용",
  "issues": "모델 성능 향상과 실제 서비스 적용 사이의 간극이 주된 논쟁이다.",
  "implications": "기업은 인프라 비용과 운영 안정성을 함께 고려해야 한다."
}
```

#### 비교 프롬프트

입력:
- 동일 이슈의 여러 기사 정보

출력:
- JSON 객체
- 키: common_facts, source_emphasis, expression_differences, keyword_differences, perspective_implications

예시:

```json
{
  "common_facts": ["두 매체 모두 모델 공개와 산업 영향력을 언급했다."],
  "source_emphasis": {"A매체": "기술 성능 중심", "B매체": "시장 영향과 비용 중심"},
  "expression_differences": ["A매체는 성능을 강조했고, B매체는 비용과 전략을 강조했다."],
  "keyword_differences": ["성능, 추론, 비용, 도입"],
  "perspective_implications": ["기술 경쟁과 산업 구조 변화가 동시에 반영된다."]
}
```

### 프롬프트 버전 관리 방법

- 변경 이유, 기대 효과, 비교 기준을 문서화
- 기준 샘플과 응답 결과를 함께 저장
- 정기적으로 평가를 재실행해 버전 간 차이를 비교

## 2. 프롬프트 개선 실험 계획

### 기존/개선 프롬프트 비교

기존 프롬프트는 규칙이 단순하고, 출력 형식은 제시하지만 세부 규칙이 충분히 제한되지 않는 경우가 많습니다. 개선 프롬프트는 다음을 강화합니다.

- 추론 금지 문구 명시
- 출력 형식에 더 구체적 제약 추가
- 핵심 정보 누락 방지
- 동일 이슈 비교에서 표현 차이와 강조점을 별도 구분

예시 비교:

```text
기존: "뉴스를 요약하세요."
개선: "기사 본문만 기반으로 핵심 사실을 3문장 이내로 요약하세요. 추정, 루머, 기사 외 정보를 추가하지 마세요."
```

### 평가 기준

- 정확성: 기사 내용과 일치하는지
- 핵심정보 포함률: 주요 사실을 누락하지 않았는지
- 일관성: 같은 입력에 대해 유사한 결과를 내는지
- 길이: 너무 짧거나 너무 길지 않은지
- 구조화: JSON 파싱이 가능한지
- 비용 효율성: 입력/출력 토큰 대비 품질 유지 여부

### 실험 구성

1. 기존 프롬프트 기준 실행
2. 규칙 강화형 프롬프트 실행
3. JSON 구조화형 프롬프트 실행
4. 짧은 입력/짧은 출력형 프롬프트 실행

### 측정 방법

- 동일 기사 세트에 여러 프롬프트를 적용
- 수동 리뷰로 정확도와 핵심정보 포함률 평가
- JSON 파싱 성공률과 응답 길이 비교
- 비용과 품질의 트레이드오프를 기록

## 3. RSS/Crawl 수집 불일치 원인 및 보정 전략

### 원인

#### 날짜/시간대 차이

- RSS는 `pubDate`를 UTC 또는 지역 시간대로 제공
- 크롤링은 사이트 HTML에서 날짜를 추출하는 방식이 달라 보정 필요

#### URL 및 중복 문제

- 같은 기사가 다른 URL로 노출될 수 있음
- 일부는 `utm_` 항목이나 쿼리 파라미터만 다름

#### RSS 본문 부족

- RSS는 요약만 제공하고 본문이 비어 있는 경우가 많음
- 본문 부족으로 분석이 제목/요약 중심으로 흐를 수 있음

#### 크롤링 선택자 실패

- 사이트 구조 변경으로 CSS 선택자가 깨질 수 있음
- 광고 영역이나 관련 기사 영역이 함께 섞여 들어오는 문제

### 보정 전략

- 모든 날짜를 ISO 날짜 형식으로 정규화
- URL 정규화 및 중복 체크 수행
- `duplicate_policy`로 skip/upsert 선택
- 본문 부족 시 원문 링크를 보완수집
- 선택자 실패를 로그로 남기고 팝업/예외 처리 추가

### 검증 방법

- 제목/URL/날짜 유효성 검사
- 중복 기사 여부 재검증
- 동일 이슈 그룹화 후 source별 비교표 확인
- 로그를 확인해 수집 실패 원인 추적

## 4. AI 품질 대비 토큰/비용 최적화 실험

### 목적

AI 요약과 분석은 모델 호출마다 입력/출력 토큰 비용이 발생합니다. 긴 본문을 그대로 전달하면 비용이 크게 증가하고, 너무 짧게 자르면 핵심 정보가 빠질 수 있습니다.

### 기본 측정 항목

- 입력 토큰 수
- 출력 토큰 수
- 호출 횟수
- 전체 비용 추정
- 응답 품질 점수

### 실험 그룹

1. Full-text 요약: 기사 전체 본문 사용
2. Truncated 요약: 본문 일부 절삭
3. Structured summary: 핵심 문장 중심 입력
4. Topic-only summary: 제목 + 키워드 중심 입력

### 비교 기준

- 요약 품질
- 분석 정확성
- 핵심정보 포함률
- 일관성
- JSON 파싱 성공률
- 전체 비용

### 운영 권장사항

- 긴 기사 본문은 반드시 정리 후 전달
- 요약 품질이 비슷하면 짧은 입력 형식을 우선 선택
- 모델 업그레이드 전에 비용/품질 비교 재실행

## 5. 결론

프롬프트 개선과 데이터 정규화는 이 프로젝트의 품질을 결정하는 핵심 요소입니다. 구조화된 지시, 보정된 데이터 입력, 비용 중심 실험을 반복하면 추론 품질, 안정성, 운영 효율성을 동시에 개선할 수 있습니다.
