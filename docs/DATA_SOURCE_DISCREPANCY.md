# RSS와 Crawl 수집 결과 불일치 원인과 보정 전략

## 1. 개요

RSS와 웹 크롤링은 같은 사건을 다루더라도 수집 시점, 본문 길이, 구조, 메타데이터가 달라서 결과가 서로 다르게 나타날 수 있습니다. 이 프로젝트는 둘을 동시에 사용하면서도 동일 이슈 기반 비교를 가능하게 하기 위해 보정 전략을 정리한다.

## 2. 주요 원인

### 2.1 날짜/시간대 차이

- RSS는 `pubDate`를 UTC 또는 지역 시간대 기준으로 보낼 수 있음
- 크롤링은 사이트 HTML에서 날짜 문자열을 추출하므로 타임존이 다르게 해석될 수 있음
- 동일 사건이 다른 날짜로 기록되면 비교 기준이 어긋날 수 있음

보정 전략:

- 모든 날짜를 ISO 날짜 형식으로 정규화
- `parsedate_to_datetime` 또는 수동 패턴 매칭으로 표준화
- 타임존 정보가 없는 경우 기본 로컬 시간대로 해석하되, 로그를 남기기

### 2.2 URL 및 중복 문제

- 같은 기사라도 URL이 다른 경우 동일 기사로 판단하지 못함
- RSS는 요약/인덱스 링크를 제공하고, 크롤링은 본문 페이지 링크를 추출할 수 있음
- 동일 URL이 다른 표현형으로 나타나는 경우도 있음

보정 전략:

- URL 정규화: 쿼리 파라미터, `utm_` 파라미터 제거
- `duplicate_policy`를 `skip` 또는 `upsert`으로 설정
- 같은 제목/본문 유사도를 함께 고려해 중복 여부를 보완

### 2.3 RSS 본문 부족

- RSS는 종종 기사 요약만 제공하고, 실제 본문을 포함하지 않음
- 본문이 부족하면 클래스별 분석과 비교가 제목 중심으로 흐르기 쉽다

보정 전략:

- RSS의 `content` 또는 `summary`를 보완 자료로 활용
- 본문이 부족한 경우 원본 링크를 통한 보조 수집 시도
- 요약 기반 비교와 본문 기반 비교를 구분해 사용할 것

### 2.4 크롤링 선택자 실패

- 웹사이트 구조 변경으로 CSS 선택자가 깨질 수 있음
- 일부 페이지는 광고, 관련 기사, 댓글 영역이 섞여 들어갈 수 있음
- 일부 기사는 JavaScript 렌더링 결과를 기대했는데 정적 HTML만 가져오는 경우가 있음

보정 전략:

- 크롤링 선택자 검증 로그를 남기기
- 빈 제목/빈 본문/잘못된 링크는 필터링
- 사이트별 예외 처리와 fallback 선택자 관리
- 수집 성공률을 로깅해 주기적으로 검증

## 3. 검증 및 보정 방법

### 3.1 전처리 검증

- 제목 비어 있음 여부 확인
- URL이 `http` 또는 `https`로 시작하는지 확인
- 게시일이 빈 값이거나 잘못된 형식이면 대체 처리
- HTML 태그 제거 후 텍스트 정규화

### 3.2 중복 검증

- 동일 URL skip
- 다른 URL인데 제목/키워드 유사한 기사 처리
- `issue_id`를 기준으로 동일 이슈 그룹화

### 3.3 소스별 비교 검증

- 각 source가 동일 이슈에 얼마나 많은 기사를 올렸는지 확인
- 사건의 공통 사실이 누락되지 않도록 기준 정리
- source별 강조점 차이를 비교표로 검증

## 4. 운영 권장사항

- RSS와 Crawl을 병행하되, 본문 품질이 높은 소스를 우선적으로 분석에 사용
- 동일 이슈 비교는 제목·키워드 기반의 보정 후 최종 판단
- 수집 결과를 월별로 점검해 사이트 구조 변화와 시간대 편차를 기록
- 로그와 분석 결과를 같이 저장해 재현 가능하게 만들기

## 5. 결론

RSS와 Crawl 차이는 데이터 수집 경로의 차이에서 발생하므로, 단순히 둘 중 하나를 택하는 방식보다 보정과 정규화가 핵심입니다. 본 프로젝트는 URL 중복 관리, 제목/본문 정제, 시간대 표준화, 선별 검증을 통해 두 수집 경로의 불일치를 줄이고 있습니다.
